# M0 스파이크 — 설치·실행·판정 가이드

새 제품 설계(제품설계도 v1.1 / 기술설계서 §8 M0 재정의)의 첫 검증.
케이던스가 심장이 될 수 있는지(M0-a), 곡이 발을 따라올 수 있는지(M0-b)를
실주행으로 판정한다. **이 둘이 통과되기 전에는 다음 마일스톤으로 가지 않는다.**

## 1. 설치 (레포 루트에서)

```
# 1) 파일 복사 — 이 폴더의 lib/를 레포 lib/에 그대로 병합
#    (신규 파일 3개뿐, 기존 파일은 건드리지 않음)
lib/services/cadence/cadence_engine.dart
lib/main_cadence_probe.dart
lib/main_tempo_probe.dart

# 2) 의존성 추가 — pubspec.yaml dependencies에 한 줄
  sensors_plus: ^6.1.1

# 3)
flutter pub get
```

CLAUDE.md 규칙 확인: 라이브러리 도입(sensors_plus)은 "판단해서 진행" 범주.
GPS 필터·배포 타깃·기존 설계 결정은 건드리지 않았다. 기존 파일 수정 0건.

## 2. M0-a 케이던스 (main_cadence_probe)

```
flutter run -t lib/main_cadence_probe.dart
```

실주행 프로토콜: 시작 → 폰을 평소 위치에 → 30초 구간마다 입으로 걸음 세기
(한 발 ×2) → 구간 경계마다 화면 탭(랩 마크) → 걷기↔달리기 전환 3회 포함.

| 판정 항목 | 기준 |
|---|---|
| spm 정확도 | 수동 카운트 대비 **±3spm 이내** |
| gait 전환 | 걷기↔달리기 전환을 10초 내 추종 |
| 주머니/암밴드/손 | 세 위치 모두에서 기준 충족 (위치별 1회씩) |

실패 시 튜닝 순서: `kThresholdK`(1.0~1.6) → 검출 창(5초) → 그래도 안 되면
CMPedometer 플랫폼 채널로 이관(문서의 트랙 B 원안). CSV 회수 명령은 프로브
파일 헤더에.

## 3. M0-b 템포 동기 (main_tempo_probe)

```
flutter run -t lib/main_tempo_probe.dart
```

| 판정 항목 | 기준 | 실패 시 |
|---|---|---|
| 메트로놈 지터 | p95 **30ms 이내** (화면에 실시간 표시) | Dart Timer 한계 → SoLoud 오디오 스레드 스케줄링으로 이관 |
| 케이던스 추종 | BPM이 발 변화를 3초 내 추종 (몸으로 체감) | 스무딩 상수 재조정 |
| 스템 속도 변경 | setRelativePlaySpeed의 피치 변화가 음악적으로 허용 가능한가 — **귀로 판정** | 허용 불가면 스템을 BPM 대역별(140/160/180) 3벌 제작으로 결정 (기술설계서 §8-2의 답이 됨) |

## 3.5. 합성 검증 층 (2026-08-22 추가 — 실측을 대신하지 않는다)

실주행 전에 알고리즘만 따로 못 박아두는 층. `test/cadence_engine_test.dart`가
합성 발걸음 신호(가우시안 착지 펄스 + 백색 노이즈)를 엔진에 밀어 넣는다.

```
flutter test test/cadence_engine_test.dart
```

**왜 필요한가:** 실측이 실패했을 때 "알고리즘이 틀렸나 · 파라미터가 안 맞나 ·
신호가 더러운가"를 가르지 못하면 튜닝이 추측이 된다. 알고리즘을 여기서 고정해
두면 실측 실패는 곧 파라미터/신호 문제로 좁혀진다.

**덮는 것:** spm 정확도(110~190spm, 노이즈 시드 8종) · 폰 위치별 진폭
(주머니/암밴드/손) · gait 전환 10초 · 정지 시 0 복귀 · 안정도.
**못 덮는 것:** 팔 흔들림, 노면 충격, 옷 스침, 폰 회전, 사람마다 다른 착지
패턴. **±3spm의 실제 판정은 여전히 실주행 CSV의 몫이다.**

### 이 층이 잡아낸 결함 2건 (실주행 전에 잡혔다)

1. **적응 임계에 절대 바닥이 없었다** — 가만히 서 있으면 임계가 노이즈
   크기까지 내려앉아 노이즈 봉우리를 전부 걸음으로 셌다(15초 정지 후 139spm).
   신호등 앞에 선 러너의 gait이 영영 `running`에 머물러 §2-2 잔향 판정이
   트리거되지 않는다. → `kMinStepMag = 1.5` 추가.
2. **gait hold 10초가 잔향 판정의 10초와 이중으로 쌓였다** — 스무딩 지연까지
   더해 달리기→걷기 전환이 15초를 넘었고, 그 위에 세션 상태머신이 다시
   "걷기 10초 지속"을 세면 쿨다운이 25초 뒤에 온다. → `kGaitHold`를 3초로.
   "몇 초 지속되어야 국면을 바꾸는가"는 세션 상태머신(P3)의 몫이다.

## 3.6. CSV 판정기

실주행 CSV가 도착하면 이것으로 잰다 — 눈으로 세지 않는다.

```
./tools/analyze-probe-csv.py cadence cadence_probe.csv --counts 41,44,45,43
./tools/analyze-probe-csv.py tempo   tempo_probe.csv
```

`--counts`는 랩 구간마다 입으로 센 **한 발** 수(구간 순서대로). 스크립트가
×2 해서 양발 spm으로 바꾸고 구간별 오차와 ±3spm 판정을 낸다. 미달이면 튜닝
순서(kThresholdK → 검출 창·kMinStepMag → CMPedometer 이관)를 함께 출력한다.
append 모드라 한 파일에 세션이 여러 개면 기본으로 마지막 세션을 본다
(`--session N`으로 지정).

## 4. 통과 후 다음 단계 (M1)

1. `resonance.dart`의 closeness 입력을 페이스 → 케이던스로 교체 (트랙 B 승격)
2. 고스트 타임라인(과거 러닝의 케이던스 기록)을 두 번째 입력으로 — 시차 공명 성립
3. 커밋 단위: 스파이크 통과 → 파라미터 확정 커밋 → 입력 교체 커밋 (CLAUDE.md: 작업 끝나면 그 자리에서 커밋)

## 5. 이 스파이크가 대답하는 질문 (설계 문서 연결)

- 제품설계도 §1-1 "BPM = 케이던스" — M0-b가 검증
- 제품설계도 §2-2 "발이 결정한다"(잔향 판정) — M0-a의 GaitState가 그 입력
- 기술설계서 §8-2 "스템 제작 방식" — M0-b의 귀 판정이 결정
- 검증 큐 #1 "내 발소리 토글" — CadenceEngine.steps 스트림이 그 트리거 (다음 스파이크)
