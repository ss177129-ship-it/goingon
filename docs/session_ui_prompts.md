# 고잉온 — 사운드 UX 선행 UI 개선 프롬프트

2026-08-16 시뮬레이터 진단(홈 → 준비 → 세션 → 종료 → 감정 → 리절트 전체 플로우 확인) 기반.
사운드가 얹히기 전에 세션 화면이 갖춰야 할 것들만 담았습니다.

## 실행 순서

```
프롬프트 1 (이벤트 레이어 — 구조)
  → 프롬프트 2 (세션 화면 시각 개편)
  → 프롬프트 3 (신호 피드백 루프)
  → 프롬프트 4 (규격·정리)
```

> 1번이 구조라서 맨 앞입니다. 2~3번은 1번이 만든 이벤트를 소비하는 쪽이라
> 순서를 바꾸면 두 번 고치게 됩니다. 4번은 독립적이라 언제든 끼워 넣어도 됩니다.

# ［프롬프트 1］ 공명 이벤트 레이어 — 사운드가 꽂힐 소켓 만들기

```
너는 Flutter 러닝 앱의 시니어 개발자다. 지금부터 "공명 이벤트 레이어"를 만든다.

## 배경
이 앱의 세션 화면은 두 러너의 상태를 두 원의 겹침으로 보여준다.
현재 겹침 정도는 연속적으로만 변하고, "상태가 바뀐 순간"이라는 개념이 코드에 없다.
곧 사운드·햅틱이 추가되는데, 그것들은 전부 "순간"에 반응한다.
이 프롬프트의 목표는 UI·사운드·햅틱이 모두 구독할 단일 이벤트 스트림을 만드는 것이다.

## 디자인 기준
design/prototype_v2.html이 단일 기준. 단, 이 파일과 충돌하면 이 지시가 우선.
기존 규칙 유지: 이모지 글리프 금지, Instrument Serif 한글 폴백(NotoSansKR) 유지.

## 만들 것

1. **동기화 상태 모델** — 연속값과 이산 상태를 분리하라

   연속값: closeness (0.0~1.0) — 이미 있다면 그것을 쓰라
   이산 상태(enum): drifting(멀어짐) / approaching(다가옴) / aligned(나란히) / resonant(공명)

   상태 판정에는 반드시 히스테리시스를 넣어라:
   - resonant 진입: closeness > 0.88
   - resonant 이탈: closeness < 0.80  (진입과 이탈 문턱이 달라야 한다)
   - aligned 진입: > 0.70 / 이탈: < 0.60
   - approaching 진입: > 0.30 / 이탈: < 0.22
   문턱값은 상수 클래스 하나에 모으고 각각 주석으로 근거를 남겨라.
   진동(깜빡임) 방지가 목적이다. 문턱이 하나면 경계에서 상태가 초당 수십 번 튄다.

2. **이벤트 스트림**

   Stream<ResonanceEvent> 형태. 이벤트 종류:
   - stateChanged(from, to, at)        상태 전이
   - resonanceEntered(at)              공명 진입 (가장 중요한 순간)
   - resonanceHeld(duration)           공명 10초/30초/60초 유지 마일스톤
   - signalSent(kind, at)              내가 신호 보냄 (탭/스와이프/길게)
   - signalReceived(kind, at)          상대 신호 도착
   - milestone(kind, at)               1km 통과, 시간 마일스톤 등

3. **연속값 스무딩**

   raw closeness → 시정수 1.0초의 지수 스무딩 → smoothedCloseness
   UI는 smoothed만 소비한다. raw를 직접 그리면 화면이 떨린다.
   시정수 1.0초는 변경하지 마라 — 이후 오디오 스무딩과 같은 값이어야
   소리와 화면이 같은 속도로 움직인다. 상수 이름에 이 의도를 담아라.
   (예: kSharedSmoothingTimeConstant)

4. **데모 모드 연결**

   현재 "혼자서 먼저 체험해보기"의 가상 파트너(지수)가 이 이벤트를
   실제로 발생시키도록 연결하라. 데모 시나리오에 resonanceEntered가
   세션당 최소 2회 발생하게 하라 — 이후 사운드 테스트가 이 데모로 이뤄진다.

## 하지 말 것
- 이 단계에서 사운드·햅틱 구현 (소켓만 만든다)
- 기존 원 애니메이션 로직 변경 (다음 프롬프트에서 한다)
- 상태를 4개 초과로 세분화 (사운드 디자인이 상태 수만큼 비싸진다)

## 완료 조건
- 데모 모드 실행 시 이벤트 로그가 콘솔에 시간순으로 찍힌다
- 같은 경계값 근처에서 상태가 튀지 않는다 (히스테리시스 검증 로그 포함)
- 이벤트 스트림을 구독하는 곳이 아직 0개여도 앱 동작이 이전과 동일하다
```

# ［프롬프트 2］ 세션 화면 — "읽는 화면"에서 "느끼는 화면"으로

```
세션(러닝 중) 화면을 개편한다. 원칙: 달리는 사람은 3초 이상 화면을 못 본다.
곁눈으로 0.5초 안에 파악되지 않는 정보는 이 화면에 있을 자격이 없다.

## 디자인 기준
design/prototype_v2.html 준수 (색·라운딩·여백·서체).
나 = lime, 상대 = coral, 공명 = 골드(#D4A84B). 이 배정을 절대 섞지 마라.
이모지 금지, Instrument Serif 한글 폴백 유지.

## 변경 목록

1. **텍스트 위계 재편 — 지우는 것이 핵심이다**

   유지 (커진다):
   - 내 페이스: Instrument Serif italic, 최소 64px. 화면 좌상단 → 원 위쪽 중앙
   - 상대 상태어("나란히" 등): serif italic, 최소 40px, coralDark.
     이 단어가 이 화면의 두 번째 주인공이다

   축소·이동:
   - "km당", 상대 이름 라벨 → 유지하되 워치 스타일 캡션(11px/600/1.2 letterSpacing)

   삭제:
   - "함께 달리는 중이에요" (정보 0)
   - "탭·스와이프·길게 누르면 신호를 보낼 수 있어요"
     → 온보딩/준비 화면으로 이동. 러닝 중 안내문은 읽히지 않는다
   - "합산은 완료 후 계산돼요" → 리절트로 이동

   34px 미만 텍스트는 캡션 라벨 외에 이 화면에 존재해서는 안 된다.

2. **원 애니메이션 — 이벤트 레이어 구독**

   프롬프트 1의 smoothedCloseness와 이벤트 스트림을 소비한다.

   연속 반응:
   - 겹침 정도 = smoothedCloseness (이미 구현된 것을 스무딩 값으로 교체)
   - 겹침 영역의 색: lime과 coral의 multiply 혼합 → closeness가 높을수록
     골드(#D4A84B)에 가까워진다. "겹치면 공명색이 나온다"가 색의 물리로 보여야 한다

   순간 반응 (이벤트 구독):
   - resonanceEntered: 겹침 중심에서 골드 링이 1회 퍼진다 (0.7초, 지수 감쇠).
     동시에 HapticFeedback.mediumImpact()
   - resonanceHeld(30초 이상): 겹침 영역에 미세한 숨쉬기(스케일 ±2%, 주기 3초)
   - stateChanged: 상태어 텍스트가 크로스페이드로 교체 (0.4초)

   구현 제약:
   - CustomPainter + AnimationController(vsync), repaint에 컨트롤러 연결
   - setState로 매 프레임 리빌드 금지
   - 원 영역을 RepaintBoundary로 격리
   - 화면이 꺼지면(AppLifecycleState) 애니메이션 컨트롤러를 완전히 멈춰라.
     러닝 앱에서 배터리 소모는 삭제 사유다

3. **공명 카운트(골드 숫자) 의미 부여**

   현재 우상단/하단의 골드 숫자가 무엇인지 화면만 봐서는 알 수 없다.
   - 공명 진입 횟수라면: resonanceEntered 이벤트와 시각적으로 연결하라
     (링이 퍼질 때 숫자가 +1 되며 살짝 튀어오름)
   - 다른 의미라면 지금 알려달라. 의미가 정해지기 전에는 표시하지 마라

## 하지 말 것

- 지도, 그래프, 추가 지표
```

# ［프롬프트 3］ 신호 보내기 — 반쪽 루프 완성

```
세션 화면의 신호 기능(탭/스와이프/길게)의 피드백 루프를 완성한다.

## 현재 문제
안내문은 있는데:
1. 보내는 순간 — 내가 뭘 보냈는지 시각 확인이 없다
2. 도착 — 상대에게 갔다는 확인이 없다
3. 수신 — 상대가 보낸 신호를 내가 받는 경험이 없다
송신 UI만 있고 경험이 비어 있다. 곧 사운드가 이 루프의 핵심 채널이 되므로
그 전에 시각·햅틱 루프를 먼저 완성한다.

## 신호 종류 확정 (3개로 제한)
- tap        "여기 있어" — 가벼운 존재 확인
- swipe      "힘내" — 응원
- longPress  "천천히 가자" — 페이스 조절 제안
의미는 위 정의를 기본으로 하되, 기획 문서에 다른 정의가 있으면 그것을 따르고
내게 알려달라. 신호는 3개를 초과하지 마라 — 달리면서 기억 못 한다.

## 만들 것

1. **송신 피드백** (내 화면)
   - 제스처 인식 즉시: 내 원(lime)에서 해당 신호의 잔상이 상대 원 방향으로
     흘러간다 (0.5초). HapticFeedback.lightImpact()
   - 프롬프트 1의 signalSent 이벤트 발행

2. **수신 표현** (상대가 보냈을 때)
   - 상대 원(coral)이 신호 종류별로 다르게 맥동한다:
     tap = 1회 펄스 / swipe = 물결 2회 / longPress = 느리고 큰 팽창 1회
   - HapticFeedback: tap = light / swipe = medium ×2 / longPress = heavy
   - 화면을 안 봐도 햅틱만으로 세 신호가 구분되는지가 설계 기준이다
   - 텍스트 표시는 하지 마라. 신호는 언어가 아니라 감각이어야 한다

3. **데모 파트너 연동**
   - 데모 모드의 지수가 세션 중 각 신호를 최소 1회씩 보내오게 하라
   - 내가 신호를 보내면 5~15초 안에 지수가 응답할 확률을 넣어라
     (신호를 보냈는데 아무 일도 없으면 다시는 안 보낸다)

4. **송신 쿨다운**
   - 같은 신호 연속 송신은 10초 쿨다운. 스팸 방지.
   - 쿨다운 중 제스처는 무시하되 시각적 에러 표시는 하지 마라
     (러닝 중 에러 UI는 죄책감 장치다)

## 하지 말 것
- 신호에 텍스트 메시지·이모지 첨부
- 4개 이상의 신호
- 신호 히스토리 UI (리절트에서 다룰 문제)

## 완료 조건
- 화면을 가리고 햅틱만으로 세 신호를 구분할 수 있다 (직접 테스트)
- 데모 세션에서 송신→응답 루프가 최소 1회 완결된다
```

# ［프롬프트 4］ 규격·정리 — 작지만 지금 해야 하는 것들

```
세션 플로우의 규격 미달과 색 규칙 위반을 정리한다. 각 항목은 독립적이다.
하나씩 수정하고 각각 별도 커밋으로 분리하라.

1. **멈춤 버튼 확대**
   러닝 중 주요 조작은 최소 72pt 터치 타겟. 현재 멈춤 버튼을 72pt 이상으로,
   화면 하단 가장자리에서 16pt 이상 띄워라.
   길게 누르기 + 확인 다이얼로그 패턴은 잘 되어 있으니 유지하라.
   길게 누르는 동안 버튼 주위에 진행 링(원형 게이지)을 추가하라 —
   지금은 얼마나 눌러야 하는지 알 수 없다.

2. **골드 사용 정리**
   골드(#D4A84B)는 공명 전용이다. 리절트 화면의 kcal 숫자가 골드로 표시되고
   있다면 ink 또는 mid로 바꿔라. 코드베이스 전체에서 resonance 색 사용처를
   검색해 공명과 무관한 곳을 전부 보고하고 수정하라.

3. **탭 반응 일관성**
   모든 탭 가능 요소: 누르는 즉시(0ms) 스케일 0.97 + HapticFeedback.selectionClick().
   현재 준비 화면 "다음" 버튼, 감정 칩, 리절트 버튼에 눌림 반응이 있는지
   확인하고 없으면 추가하라. 공통 위젯으로 추출해서 중복을 없애라.

4. **공유하기 확인**
   리절트 화면의 "오늘의 순간 공유하기"가 시뮬레이터에서 무반응이었다.
   미구현이면 숨겨라 — 눌러서 아무 일도 없는 버튼은 앱 전체의 신뢰를 깎는다.
   구현되어 있다면 시뮬레이터 한계인지 확인해서 보고하라.

5. **세션 화면 밝기 대응 확인**
   paper 배경(#F0EAE0)은 야외 직사광에서 유리하지만, 새벽·야간 러닝에서
   눈부실 수 있다. 시스템 다크모드 대응이 현재 있는지 확인만 하고 보고하라.
   (구현은 하지 마라 — 다크 세션 화면은 별도 설계가 필요하다)

각 항목 완료 시: 무엇을 바꿨는지 한 줄 + 스크린샷.
```

## 이 문서에 없는 것 (의도적)

- **사운드 구현** — 위 4개가 끝나면 이벤트 레이어에 오디오 구독자를 붙이는
  일만 남습니다. 그때 사운드 UX 스펙(어떤 이벤트에 어떤 소리)을 따로 만드세요.
- **다크모드 세션 화면** — 확인만 하고 설계는 뒤로.
- **리절트 화면 심화** (싱크 그래프, 공유 카드 디자인) — 별도 트랙.

## 왜 이 순서인가

사운드는 "순간"에 반응합니다. 지금 앱은 연속값만 있고 순간이 없어서,
사운드를 먼저 만들면 꽂을 데가 없습니다. 프롬프트 1이 순간을 만들고,
2와 3이 그 순간을 시각·햅틱으로 먼저 소비해봅니다. 여기서 순간의 타이밍이
맞는지 검증되면, 사운드는 같은 소켓에 꽂기만 하면 됩니다.
